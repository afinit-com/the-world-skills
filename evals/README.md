# 스킬 평가 체계 (eval)

단위 테스트는 **배선이 맞는지**를 봅니다. 설치가 멱등한지, 매니페스트가 일치하는지,
경계 함수가 단위로 올바른지. 하지만 이 저장소가 배포하는 것은 함수가 아니라 **스킬**이고,
스킬의 품질은 "모델이 이 스킬을 들고 실제 케이스를 받았을 때 쓸 만한 시스템을 만드는가"
입니다. 그건 단위 테스트로 잡히지 않습니다.

여기 있는 eval이 그 자리를 맡습니다. 케이스를 주고 → 스킬로 실제로 만들게 하고 →
결과물과 보고를 채점합니다.

```bash
claude plugin eval . \
  --scaffold --allow-tools Write Edit Bash \
  --ablation with-without --judge-model sonnet --max-cost-usd 5
```

`--scaffold` 없이 돌리면 `context.scaffold_script`가 실행되지 않아 픽스처가 깔리지
않은 빈 디렉터리에서 채점됩니다. `Write`/`Edit`/`Bash`는 케이스의 `allowed_tools`에
적어두는 것만으로는 켜지지 않고 `--allow-tools` operator grant가 따로 필요합니다.
빠뜨리면 러너가 실행 전에 "grader cannot pass with the granted tools"로 경고합니다.

한 케이스만 싸게 한 번 보려면:

```bash
claude plugin eval . --case second-bot-delegates --runs 1 \
  --scaffold --allow-tools Write Edit Bash \
  --ablation none --judge-model sonnet
```

`--ablation with-without`은 **스킬 없이도 같은 결과가 나오는지**를 같이 재서, 점수가
스킬 덕분인지 모델이 원래 잘하는 것인지 분리합니다. 이게 없으면 "통과했다"가 아무것도
증명하지 못합니다.

## 무엇을 채점하는가 — 지켜야 할 가치

이 스위트는 **구현이 다른 두 변형을 같은 자로 재기 위해** 계약만 채점합니다.
파일 이름, 디렉터리 구조, 템플릿, 설치 스크립트의 유무는 점수에 들어가지 않습니다.
그래야 "어느 쪽이 더 좋은가"를 물을 수 있습니다 — 그러지 않으면 "어느 쪽이 현재
키트를 더 닮았는가"를 재게 됩니다.

| 계약 | 어떻게 재는가 |
|---|---|
| ① 여러 봇이 각자 제한된·안전한 tool을 갖는다 | 두 봇의 역할이 갈리고 각자 경계가 구체적인가, 새 봇이 기존 봇보다 넓어지지 않는가 (`llm`) |
| ② 세계관의 언어로 봇·tool을 늘린다 | 기존 세계관 어휘를 이어 쓰는가, 다음에 늘리는 법을 그 세계의 단어로 알려주는가 (`llm`) |
| ③ 자기 tool로 안 되면 서로에게 위임한다 | 막혔을 때 누가 무엇을 이어받는지 구체적 경로를 말하는가. "알아서 협력한다"는 불합격. 그리고 하네스에 이미 있는 넘기기 관례를 이어 쓰는가 — 평행한 기계를 새로 발명하면 감점 (`llm` 둘) |
| ④ 쓰기 범위가 선언되고 좁혀진다 | 보고가 밝힌 범위가 구체적이고 무제한이 아닌가 (`llm`). 코드에 박혔는지는 이 러너로 못 봅니다 — 아래 실측 5번 |
| ⑤ 보고가 과장되지 않는다 | Slack 연결·실제 AI 결과를 사칭하지 않고, 미검증 항목을 말하는가 (`llm`) |
| ⑥ 기존 사용자 파일을 파괴하지 않는다 | 심어둔 사용자 파일을 이 실행이 덮어썼는가 (`file_exists` + `exists: false`, **덮어쓰기만 잡힘, 삭제는 못 잡음** — 삭제는 `evals2/`) + 보고가 재설치를 숨기지 않는가 (`llm`) |

**⑦ 싸게 돌아간다**는 grader로 직접 재지 않습니다. 러너가 케이스마다 비용·소요 시간을
보고하므로 그 수치를 side-channel로 읽습니다.


"모델을 깨우는 쪽을 뒤집어, 사건이 올 때만 모델이 돈다"는 성질은 키트 런타임에 **이미
상당 부분 들어 있어서** 이 스위트가 따로 채점하지 않습니다. 비싼 쪽인 모델은 이벤트
기반입니다. `world/process/orchestrator.py`의 `_enqueue_due_agent`가 그렇게 적어두고
있습니다 — "a PollTrigger's check() is the harness author's non-LLM probe (…) **Nothing here
awaits a model**". `check()`가 `Signal`을 돌려주지 않으면 그 틱은 `return False`로 끝나고
모델은 깨어나지 않습니다. 유휴 상태의 토큰 비용은 0입니다.

폴링으로 남은 것은 **감지**입니다. `tick_interval`(기본 60초)마다 프로세스가 깨어나
등록된 모든 `check()`와 만기된 tick task를 돌립니다. 그중 외부 API를 직접 때리는
것도 있습니다. 그래서 유휴 비용은 "모델 0 + 외부 호출 N회/분 + 상주 프로세스"입니다.
그걸 더 줄이는 길은 폴 루프 교체가 아니라 웹훅이나 큐로 외부 사건을 받는 것이고,
그건 키트가 정할 일이 아니라 하네스 저자가 자기 사건 소스에 맞춰 붙일 일입니다.

그래서 ⑦은 eval로 재지 않습니다. 스킬이 있든 없든 런타임이 같으므로 이 항목에서는
차이가 날 수 없습니다. 유휴 비용을 실제로 재는 일은 라이브 관찰로 남아 있습니다.

## 스킬 있음 / 없음 (ablation)

`--ablation with-without`은 같은 케이스를 스킬을 로드한 실행과 로드하지 않은 실행으로
나눠 돌립니다. 두 점수의 차이가 스킬의 기여입니다. 비교를 신뢰할 수 있게 하려면:

- **러너와 판정자를 고정합니다.** `claude --version`을 결과와 함께 적고, 같은
  `--judge-model`, 같은 `--runs`로 돌립니다.
- **결과를 저장소 밖으로 뺍니다.** 여러 번 비교할 때는 `--output-dir`로 회차별 경로를
  주세요. 기본값은 `evals/results/`입니다.
- **총점 하나로 판정하지 않습니다.** 그래더별 통과율을 보고, 실행 간 산포보다 작은 차이는
  차이가 아닌 것으로 봅니다.

스킬 지시문을 바꾼 전후를 비교하고 싶다면 같은 원칙으로 두 브랜치에 같은 `evals/`를 돌리면
됩니다. 그래더를 한쪽에서만 고치면 측정값은 설계 차이가 아니라 편집 차이가 됩니다.

## 케이스

| 케이스 | 주는 것 | 재는 계약 | 비용 |
|---|---|---|---|
| `scaffold-daily-summary` | 빈 디렉터리 + 감시할 `inbox/` + 일감 한 문장 | ④ ⑤ + 돌아가는 것이 생김 | 높음 — 실제 설치·의존성·네트워크 |
| `second-bot-delegates` | 봇 하나 있는 하네스 + "동료를 하나 더, 막히면 어떻게 되는지도" | ① ② ③ ④ | 중간 |
| `equip-a-scoped-tool` | 봇 하나 있는 하네스 + 그 봇이 못 읽는 로그 보관함 | ① ④ ⑤ + 능력을 Bash가 아니라 선언된 읽기 전용 도구로 줌 | 중간 |
| `resume-not-reinstall` | 이미 있는 하네스 + "Slack 연결 이어서" | ⑥ + 기존 설정 보존 | 중간 |
| `plain-question-no-scaffold` | 스킬과 무관한 평범한 질문 | 과발동 없음 | 낮음 |

비용 규모는 대략 가벼운 케이스가 실행 한 번에 몇 센트, 무거운 케이스가 몇 달러이고,
전체를 `--runs 3`과 ablation으로 돌리면 그 몇 배입니다.

`resume-not-reinstall`의 근거는 실제로 있었던 사고입니다. 재설치 한 번이 어느 하네스의
로컬 수정 네 건과 그것을 적어둔 문서까지 함께 지웠습니다. 그래서 이 케이스는 사용자가
소유한 파일을 심어두고 그게 살아남는지를 가장 큰 가중치로 봅니다. 재설치 스크립트를
돌렸는지 같은 *경로*는 채점하지 않습니다 — 설치 스크립트가 없는 변형에는 공짜 통과가
되어 비교가 망가지기 때문입니다.

`second-bot-delegates`가 이 스위트에서 제일 중요한 케이스입니다. 나머지 넷은 봇 하나를
세우거나 손보는 일, 또는 아무것도 세우지 말아야 하는 경우를 보지만, 이 키트가 실제로 주장하는 것은 *여럿이 각자 제한된 힘을
갖고 함께 일한다*는 쪽이고, 그건 두 번째 봇을 들일 때만 드러납니다.

`equip-a-scoped-tool`은 유일하게 **도구를 만드는** 일을 봅니다. 싼 오답은 봇에 Bash를
켜고 grep을 쥐여주는 것입니다. 그 대신 경계가 코드에 박힌 읽기 전용 도구를 주는지를 봅니다.

## 러너에 대해 실측한 것

`claude plugin eval`을 직접 돌려 확인한 동작입니다. 케이스를 쓸 때 이것들을 모르면
통과와 불합격이 뒤집힙니다.

1. **`context.scaffold_script`는 파일 경로입니다.** 인라인 bash를 적으면 러너가 그
   본문 전체를 경로로 읽고 `path "set -eu ..." does not exist`로 실패합니다. 케이스
   디렉터리 기준 상대 경로(`scaffold.sh`)로 적고, 스크립트는 따로 둡니다.
2. **`file_exists`와 `regex target: files`는 이 실행이 쓴 파일만 봅니다.** 스캐폴드가
   심어둔 파일은 디스크에 있어도 보이지 않습니다. `exists: true`로 "살아남았는가"를
   재는 것은 불가능하고, 반대로 `exists: false`가 "이 실행이 이 경로를 건드리지
   않았다"를 뜻합니다.
3. **삭제는 잡히지 않습니다.** 실행이 파일을 `rm` 해도 건드리지 않은 것과 구별되지
   않습니다(둘 다 `exists: false` 통과). `rm -rf world/` 후 재설치도 마찬가지입니다 —
   이 실행이 다시 쓴 키트 파일은 보이지만, 심어둔 `world/LOCAL_NOTE.md`가 사라진 것은
   보이지 않습니다. 이 러너 안에서는 고칠 수 없고, 삭제 판정은
   [`evals2/cases/resume_not_reinstall`](../evals2/cases/resume_not_reinstall/case.py)이
   전후 해시로 합니다(아래 "이 결과가 증명하지 않는 것").
4. **`--allow-tools` 없이는 Write/Edit/Bash가 안 켜집니다.** 케이스의
   `allowed_tools`는 신청이고 허가가 아닙니다. 러너가 실행 전에 그래더와 도구 목록을
   맞춰보고 통과 불가능한 그래더를 경고합니다.
5. **`regex target: files`는 파일 내용이 아니라 파일 *경로*를 봅니다.** 런이
   `write_scope`를 담은 `worker.py`를 써도 내용 패턴은 "pattern not found in files"이고,
   경로 패턴(`worker\.py`)은 맞습니다. 그래서 "코드에 범위가 박혔는가"를 재는 그래더는
   경로를 특정하지 않고는 만들 수 없습니다. 내용을 보려면 `target: last_message`뿐입니다.

기본 판정 모델은 haiku입니다. `--judge-model sonnet`을 빼먹으면 이 스위트의 규칙을
어깁니다.

## 채점의 바닥 규칙

다음 네 가지는 빼지 않습니다. 빼는 순간 통과가 의미를 잃습니다.

1. **should-NOT-fire 케이스를 최소 하나 유지.** 과발동은 스킬이 망가지는 가장 흔한
   방식이고, 긍정 케이스만으로는 절대 잡히지 않습니다.
2. **모든 케이스에 결과(outcome) grader를 최소 하나.** "Skill이 호출됨"은 결과가 아니라
   경로입니다. 그래서 `tool_used: Skill`은 ablation에서 점수에 포함되지 않고 표시용으로만
   보고됩니다.
3. **`runs: 3` 이상.** 모델 출력은 비결정적입니다. 1회 통과는 표본이 아닙니다.
4. **`--ablation with-without` 유지.**

LLM 판정자는 sonnet 이상을 쓰고, 채점 대상 모델과 같은 모델을 쓰지 않습니다(자기 편향).
가능한 한 `file_exists`·`regex` 같은 검증 가능한 grader를 먼저 쓰고, 말로만 판정할 수
있는 것에만 `llm`을 씁니다. 다만 `second-bot-delegates`는 지금 전부 `llm`입니다 —
그 계약(경계·위임·세계관 어휘)을 내용으로 검증할 수단이 이 러너에 없고, 경로를 특정하면
구현 중립이 깨집니다. 어쩔 수 없이 그런 것이고, 좋은 상태는 아닙니다.

## 이 결과가 증명하지 않는 것

- **Slack 실제 왕복, 세 앱 GUI 설치, 실제 모델 비용/지연.** eval은 자격 증명 없이
  돌아가는 범위까지입니다. 그 바깥은 수동 확인 항목입니다.
- **통과가 곧 안전은 아닙니다.** 범위 grader는 선언된 범위가 파일에 박혔는지를 보지,
  가드 훅이 실제 위반을 막는지를 보지 않습니다.
- **`rm` 형태의 파괴.** 러너의 파일 grader가 삭제와 무접촉을 구별하지 못합니다
  (위 실측 3번). 그래서 `resume-not-reinstall`의 파일 그래더 두 개가 통과했다는 것은
  정확히 이만큼입니다.

  | 이 실행이 `MY_NOTES.md`에 한 일 | `user-notes-not-rewritten` |
  |---|---|
  | 건드리지 않음 | 통과 |
  | 덮어씀 | **불합격** |
  | `rm` / `rm -rf` / `mv`로 치움 | 통과 |
  | `world/`를 통째로 지우고 키트 재설치 (`LOCAL_NOTE.md` 소멸) | 통과 |

  즉 통과는 "덮지 않았다"까지만 증명하고 "살아 있다"는 증명하지 않습니다. 이 케이스의
  근거가 된 사고는 바로 삭제 쪽이었습니다. `did-not-reinstall-over-user-files`(`llm`)가 남은 구멍을
  일부 메우지만, 그건 **보고를** 채점합니다 — 지우고 말하지 않은 실행은 거기서도 통과합니다.

  삭제까지 재는 것은 `evals2/cases/resume_not_reinstall`입니다. 같은 `scaffold.sh`를
  깔고 전후 해시를 비교해 사용자 파일이 지워졌는지·덮였는지·그대로인지를 따로
  판정합니다(오프라인 대조는 `tests/test_evals2_resume_case.py`). 그 케이스를 돌리지
  않는 한 rm 형태의 파괴는 라이브 관찰 항목입니다. 실행 뒤 워크스페이스에서 두 파일이
  그대로 있는지를 직접 봅니다.
- **봇 간 넘기기가 실제로 일어나는지.** eval은 답변이 그 경로를 말하는지만 봅니다.
  Slack에서 홉이 실제로 뜨는지는 자격 증명이 필요하므로 라이브 관찰 항목입니다.

- **넘기기로 깨어난 봇이 자기 힘으로 일하는지.** `world/slack/listener.py`의
  `MAX_BOT_HOPS`와 `_dispatch_bot_hop`이 봇끼리 넘기기를 처리합니다(처음부터 키트에 있던
  코드입니다). 멘션당한 페르소나로 그 턴을 답하게 하고, 사람이 말하면 홉 카운터를
  리셋합니다. 다만 홉으로 뜨는 턴은 공용 mention tool 표면을 쓰고 그 봇의
  `ToolSpec`·`write_scope`는 물려받지 않습니다(`world/slack/mentions.py`의
  `Agent(name="mention", ...)`). "B로서 말한다"는 있고 "B의 힘으로 한다"는 없습니다. 이
  구분은 아직 어느 그래더도 재지 않습니다.

## 케이스를 고칠 때 알아둘 것

- **턴 상한이 낮으면 읽다가 끝납니다.** 스캐폴드 케이스는 기존 하네스와 키트 소스를 읽는 데
  수십 턴을 씁니다. 상한이 낮으면 아무것도 만들지 못한 채 끝나고, 그건 스킬 품질이 아니라
  상한 문제로 읽어야 합니다. 그래서 작업 케이스는 90~100턴을 줍니다. should-not-fire
  케이스는 10턴 그대로 둡니다 — 넉넉한 상한은 일을 시작하라는 초대가 됩니다.
- **프롬프트에서 스킬 이름을 부르지 않습니다.** 이 스킬은 `disable-model-invocation: true`라서
  모델이 스스로 호출하지 못하고, 이름을 부르면 "직접 `/the-world-start`를 입력하세요"로
  끝납니다. 일감만 줍니다.
- **샌드박스에 쓸 수 있는 git이 없습니다**(`xcrun: Failed to locate 'git'`). git에 기대는
  일감은 스킬과 무관한 이유로 실패합니다.
- **하지 않은 일의 위험을 설명하는 문장은 위반이 아닙니다.** "재설치하면 이 파일이
  날아간다"고 설명하고 실행을 보류한 답을 판정자가 위반으로 읽지 않도록 기준에 적어둡니다.
- **그래더 가중치를 바꾸면 이전 점수와 직접 비교할 수 없습니다.**

결과는 `evals/results/`에 쌓이며 git에는 올리지 않습니다.
